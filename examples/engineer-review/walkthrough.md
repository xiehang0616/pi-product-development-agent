# 分轮操作与对照要点

以下内容是教学样稿，不是 Pi Agent 的真实会话日志。推荐方案和确认消息仅适用于这个虚构练习。

## 首轮：检查后应报告什么

若你按示例准备了空目录，Agent 应报告发现一份简短 PRD，未发现应用代码、测试框架或模型配置。若目录实际不同，应按实际文件报告，不能照抄这里的环境结论。

### 输入已明确

- 用户需要根据文本获得字段建议，查看依据，并能修改或放弃。
- AI 不能直接应用建议；正式写入前需要人工确认。
- 当前只有需求输入，尚不能报告应用可运行或模型效果。

### 最影响下游的三个问题

1. **权限与复核责任：** 谁能申请、复核、应用；是否要求双人复核？影响角色、接口鉴权和测试。
2. **写入范围与版本：** 哪些字段能改；记录变化后是否允许继续应用？影响字段契约、状态转换与一致性。
3. **异常与验证范围：** 如何处理无依据和错误输出；本阶段用模拟结果还是实际模型？影响界面状态和验收证据。

### 三个推进方案

| 方案 | 做法 | 收益与代价 |
| --- | --- | --- |
| A：先确认最小复核流程（推荐） | 明确角色、字段、状态和版本规则，用模拟结果设计验收 | 能形成可检查的需求；模型效果仍需后续验证 |
| B：先补访谈和真实样本 | 收集经授权的角色流程、输入样本与失败案例，再收敛范围 | 更接近真实使用；需要额外资料与时间 |
| C：只做只读建议演示 | 暂不设计应用写入，仅展示建议、依据和异常状态 | 更快比较展示体验；无法验证正式写入闭环 |

本例推荐 A，因为当前可以先确定复核与写入边界，而模型选型缺少样本与指标。实际项目若条件不同，Agent 应重新说明推荐理由。

## 第二轮：教学用确认消息

阅读下面的演示规则后，若决定按它练习，可以复制发送：

```text
本次练习选择方案 A，仅完成需求文档与研发任务拆解。
以下是这个虚构示例的确认规则，不代表任何真实系统的已确认规则：

1. 只处理文本，不处理真实图纸。所有示例数据都是虚构数据。
2. 角色分为工程师和只读查看者，只能访问各自授权项目。
   工程师可以申请、复核和应用；本轮不要求双人复核。
3. AI 只能建议资料编号、材料名称和备注，未知字段留空并说明缺少依据。
   项目、权限、记录标识与记录版本不允许由 AI 修改。
4. 使用待复核、已复核、已应用、已作废四种建议状态。
   复核后再次编辑内容须重新复核。放弃建议或发现原记录版本变化时作废。
5. 申请时记录原记录版本；应用前由服务端再次检查权限、版本和状态。
   成功写入、建议状态和审计记录应一致提交；重复应用不得重复写入。
   若权限失效则拒绝；若版本冲突则作废并要求重新申请；普通写入失败允许重试。
6. 不接真实模型，只规划模拟结果下的功能验收，不设定模型质量达标结论。

允许更新练习目录里的 docs/PRD/PRD.md，
并新建 docs/项目状态/项目状态.md 与 docs/测试Case/测试Case.md。
记录上述规则来自本轮确认消息，保留尚未确定的技术栈和模型事项。
每项研发任务写清依赖、交付物和验收条件。
不要实现应用、安装依赖、运行付费服务或生成已通过的测试报告。
文档整理完成后停止并报告待确认项。
```

## 第三轮：检查与继续

对照 [PRD](expected/docs/PRD/PRD.md)、[项目状态](expected/docs/项目状态/项目状态.md) 和[测试 Case](expected/docs/测试Case/测试Case.md)，按含义检查，不要求逐字匹配。

一个合适的结束报告应说明：已整理了哪些文档、确认规则来自哪里、哪些技术选择仍待确认，以及未实施、未测试、未评测的范围。不能因为生成了用例，就把任务标成已通过。

如需进入开发阶段，可以继续发送：

```text
请先阅读项目状态和 PRD，说明下一阶段需要确认的产品设计与技术方案。
结合当前项目实际环境给出方案和依赖；先不要实现，也不要把推荐方案写成我的决定。
```
